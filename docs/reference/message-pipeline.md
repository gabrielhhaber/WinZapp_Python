# Message/data pipeline

> The full walk from Socket.IO to SQLite: funnels, dedup, echo matching, ciphertext placeholders, the DB bridge, video player.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## Message/data pipeline
1. **`client/core/websocket_client.py`** (`WebSocketClient`) connects to WPPConnect's Socket.IO and normalizes raw WPPConnect/Baileys event payloads into WinZapp's canonical message dict shape: `{"key": {"remoteJid", "fromMe", "id", "participant"?}, "message": {...}, "messageType": "...", "messageTimestamp": ..., "pushName": "..."}`. All downstream code (`main.py`, `core/database.py`, `ui/conversations.py`) assumes this shape.
2. **`MainWindow.on_new_message()`** (live messages) and **`on_historical_message()`** (history-sync backfill) in `client/main_window/message_events.py` are the two funnels every incoming/echoed message passes through: they resolve `@lid`↔phone duplicates, match echoes of our own sends against locally-registered "pending" virtual messages, update in-memory `self.chats`, and schedule a debounced persist. Both — plus `_extract_lid_mapping()`, which `WebSocketClient.on_messages_upsert()` also calls directly on the Socket.IO thread, bypassing the other two entirely — are gated by `MainWindow._live_events_ready()`: a reused pairing WebSocket can start delivering events before `prepare_sync()` has created `self.db`, or before the initial sync has actually started, and processing a message that early either crashes (attribute doesn't exist yet) or lets a live event sneak a chat into the list ahead of the sync about to fetch the authoritative state. `is_countable_message()` (plain function in `client/main_window/message_rules.py`) further excludes WhatsApp/WPPConnect system events (`groupNotification`, `protocolMessage` — group join/leave, settings changes, revokes) from ever bumping a chat's sort position, incrementing its unread badge, or firing a notification; they're still stored and shown as a timeline entry when the conversation is opened. **Edits**: WhatsApp re-delivers an edited message under its *original* `key.id` — `on_new_message()`'s same-id dedup check routes that into `_apply_possible_edit()`, which compares old vs. new text and updates the stored record in place if it changed. This only works live because `client/api_patches/src/util/createSessionUtil.ts` explicitly listens for wppconnect's `onMessageEdit` event and re-emits it through the same `'received-message'` Socket.IO event as a normal new message — an edit from someone else never fires `onAnyMessage` at all, so without that explicit listener the edit would be silently dropped server-side and never reach Python. **An edit also has a second shape, and it is the one that duplicates rows**: `WPP.chat.editMessage()` also creates a separate `type: "protocol"`, `subtype: "message_edit"` message with a *new* id, `protocolMessageKey` naming the original and `body` holding the new text, and WhatsApp Web keeps it in the chat's messages — so `get-messages` returns it. The normaliser used to turn it into plain text through its "unmapped type with body" fallback and the id-based merge appended it: reproduced live as an edited reply gaining an unquoted copy of itself under it at the next 60 s poll, only on the editor's side. It is now mapped to a hidden `protocolMessage` and **dropped, never applied** — the onMessageEdit re-delivery above already carries the full current message — by `_drop_protocol_edit()` in `on_new_message()`/`on_historical_message()` (before either can create or restore a chat) and by `is_edit_event()` in `_normalize_fetched_messages()` and `fetch_older_messages()`, which also purge a copy already stored under the event's id (`core/message_edit.py`). Any new consumer of `get-messages` that normalises by hand must filter it too, or the duplicate comes back through that one.
3. **`ciphertext` is a placeholder, not a message.** WhatsApp Web delivers each message twice: a `ciphertext` envelope first, then the decrypted copy under the *same* `key.id` (2.5 s and 4.2 s apart in the two occurrences measured). Storing the placeholder made the real one look like a duplicate: `on_new_message()`'s same-id dedup routed it into `_apply_possible_edit()`, which never announces anything, while the placeholder itself is correctly non-countable — so WhatsApp's own `unread=1` was discounted back to zero. A voice message arrived with no sound, no badge, no screen-reader announcement, and the row read "Mensagem incompatível" until a later poll rewrote it. `_is_undecrypted_placeholder()` drops it before storage, after `_extract_lid_mapping()` (the envelope's addressing is real even when its content is not). Deliberately a separate frozenset from `is_countable_message()`'s allowlist: `e2e_notification` and friends are *stored* and merely uncounted, and conflating the two lists is how a real type gets dropped. **A sync still stores it**: `get-messages` returns what WhatsApp Web's store holds, and a message that device cannot decrypt ("Aguardando mensagem" — typically every message from one sender who changed phone, until that phone answers WhatsApp's retry) stays a `ciphertext` there, possibly for hours. Such a row used to be hidden (not a displayable type), so a reply quoting it pointed at nothing — reported 2026-09-23, 165 rows on one install; it is now shown as `message_awaiting_decryption` ("Aguardando mensagem…", as WhatsApp itself does), and still never counted nor a chat preview. When the decrypted copy finally arrives live, the same-id dedup must not hand it to `_apply_possible_edit()` (a placeholder has no text, so it was silently discarded): `_resolved_placeholder_is_fresh()` sends a copy that is still the newest record and within the 60 s notification cutoff down the full new-message path, and `_fill_stored_placeholder()` fills any other one in place and rebuilds the open list through `refresh_messages_if_changed()`. **A reply fills it sooner**: its `contextInfo` carries the original's id, author and text, read on the replier's phone. `core/quote_recovery.py` fills the placeholder from that quote — text only (media is fetched by id, still a ciphertext), never a quote exactly `QUOTED_TEXT_CAP` long (the stored reply may have cut it), and only when the quote names the placeholder's own author. The record is marked `_recovered_from_quote`: `awaits_real_copy()` makes the dedup replace it with the real copy instead of reading that as an edit, and `carry_over_known_content()` stops a sync copy that is still a ciphertext from wiping it. **Nor does any other known content give way to a ciphertext**: a message this account sent from the other engine (switching from Neonize to WPPConnect, a message just sent to a group came back as one), or one decrypted earlier, keeps its text in the sync (`carry_over_known_content()`) and in the database (`_apply_known_local_fields()` with `keep_known_content()`), so F5 and a restart show it too. Only a message whose id is gone, or whose copy is `revoked`, stops showing. It runs in both funnels (an older placeholder is found on disk through `get_message_by_id()`), in `sync_chat_messages()` before its batch write and outside the persist `try`, and once at startup for pairs already stored. Measured on the reporting install: 29 placeholders quoted by a reply, 14 recovered, the other 15 quoted media.
3a. **Calls are messages too.** WhatsApp Web keeps every voice/video call as a `call_log` message in its chat, whose id is the call id (measured over CDP 2026-09-24). The normaliser maps it to `callLogMessage` (`core/call_log.py`: outcome, video flag, duration); it renders like a system event (no sender, reply/react/forward/star/pin refused), is a chat preview but never countable. **The record is rewritten in place**: a call placed or answered here is first written as `Ongoing` and updated to its outcome when it ends (`updateVoipCallLogOutcomeImpl`), and that update never fires `onAnyMessage`. So `_watch_ended_call_log()` (on every ended call) and `_watch_pending_call_log()` (on a recent `Ongoing` record) poll `message-by-id` on a bounded schedule, and both funnels replace the stored record when `call_log_supersedes()` says the copy is newer. Records stored by older builds are the raw `call_log` type with no call data, and read as a generic "Ligação" until a sync of that chat replaces them.
4. **Outgoing sends**: UI code in `client/ui/conversation_panel/text_sending.py` (and `attachments.py`, `voice_recording.py`) builds a "virtual" pending message dict (`_local_pending: True`, `_local_id: <uuid4>`) shown immediately in the UI, and hands it to **`client/core/message_queue.py`**'s `MessageQueue` (one background thread). The queue calls the matching `send_*` method on `MainWindow` (`send_text_message`, `send_audio_message`, `send_media_attachment`, `send_contact_attachment`), which POSTs to a WPPConnect REST endpoint and returns the real WhatsApp message ID. A send failure is classified before it's retried: an explicit "Disconnected" response leaves the message queued untouched, a timeout/dropped connection is treated as *ambiguous* (WhatsApp Web may have accepted it into its own outbox already) and is handed off without a resend, and only a definite server-side failure retries — at most 4 times. This exists because retrying an ambiguous failure used to duplicate real sends when connectivity flapped. Separately, the *same* sent message also arrives back through the WebSocket echo path (`on_new_message`, `from_me=True`) — since WPPConnect gives no client-side correlation ID on that echo, it's matched against pending virtual messages **by message type** (text/audio/image/etc.), not by content. Be careful here: matching the wrong pending message swaps real WhatsApp IDs between unrelated messages (wrong status, wrong audio file playback).
5. **`client/core/database.py`** (`DatabaseManager`) is a fully async `aiosqlite` layer — single serialized connection, WAL mode, per-write `asyncio.Lock`. Indexed columns (`jid`, `timestamp`) are plaintext; payload columns (`message_json`, `last_message_json`) are Fernet-encrypted with a per-install key (`data/secret.key`). Storage is SQLite-only (`messages.db`) — there is no `messages.dat` fallback or migration path any more; that legacy format was retired.
6. **`client/core/database_bridge.py`** (`DatabaseBridge`) is the sync façade `MainWindow` actually calls: it runs a dedicated background asyncio event loop in its own thread and dispatches every `DatabaseManager` call via `asyncio.run_coroutine_threadsafe(...).result(timeout=...)`, blocking the calling (wx/worker) thread until the call finishes or the timeout elapses. This exists because wx and the rest of the app are synchronous/thread-based, but the DB layer is async. The timeout (and `close()` refusing new calls / waiting briefly for in-flight ones to drain before stopping the loop) exist specifically to keep a stuck coroutine from freezing the whole app forever — that used to be the most commonly reported "WinZapp stopped responding" symptom.
7. **In-app video/audio playback — `client/core/video_player.py`** (`VideoPlayer`): audio is decoded directly from the source file by BASS (`sound_lib`, same engine used for voice messages elsewhere), while video frames are produced by a background `ffmpeg` process piping a low-rate MJPEG sequence into a `wx.StaticBitmap` via a `wx.Timer`. Shared by `ConversationsPanel` (Enter on a video message — `_play_toggle_video_message()`, applying the conversation's configured playback speed via BASS's Tempo FX) and `StatusPanel` (Enter/Space on a video or audio status). BASS has no video output at all, hence the separate ffmpeg frame pipe; sync between the two is deliberately approximate (`ffmpeg -re` real-time pacing), not frame-exact — see the module's own docstring for the full reasoning, including the EOF/tail-cutoff race it guards against via a `_generation` counter.


## Account and peer alias boundary

Message and chat-list alternate identifiers are untrusted identity hints. `core/jid_alias_guard.py` checks them against the explicit account phone/LID, without asking the mutable mapping cache whether a candidate is self. A rejected cross-self hint must not become a routing result after registration refused it. The live/history resolver uses a safe cached peer mapping or preserves the original unresolved peer; it never drops the message to resolve this ambiguity.

History-cache reconstruction and `main_window/chat_aliases.py` apply the same boundary before learning aliases. Existing incompatible in-memory pairs are retired without editing stored messages. `_merge_lid_into_phone` also refuses a cross-self pair before touching the chat store or scheduling a database merge. Genuine self pairs, ordinary peer aliases, device suffix normalization and Brazilian mobile variants remain supported. This prevents new misfiling; it does not relocate previously misfiled records or establish installed-app acceptance.

Event and snapshot entry points retire only the incompatible cached pairs touched by their JIDs, under the existing mapping lock, before cache-based self inference or name lookup. A reverse entry is removed only if it still points to the rejected pair; an unresolved live peer can then enter the ordinary resolution queue. Snapshots without an alternate hint receive the same protection. The merge method also retains its existing phone-to-phone use for an exact Brazilian 8/9-digit variant pair; unrelated phone pairs are refused.

## A backlog delivered as live events

After a long absence WhatsApp hands the missed messages over the WebSocket *after* the sync round has ended (measured 2026-11-13, Neonize, slow link: about 1,500 `received-message` events in four minutes following a one-second sync; WPPConnect does the same). `main_window/backlog_flood.py` recognises it — several messages sent more than five minutes before they arrive, within a few seconds — and, while it lasts, shows "updating conversations" instead of an idle status and keeps `on_new_message()`, `on_historical_message()` and `on_chat_unread_update()` from touching the chat list, which is rebuilt once at the end (and once a minute if the flood goes on). Data, unread counts and the database are updated as usual. It deliberately does not touch `_sync_completed`: the health checker and the unread gate read that flag. Separately, `core/notification_burst.py` lets the first three message notifications of a burst through and stays quiet until arrivals drop under three per second (three by default; `general.notification_burst_limit`, Settings > General > Notifications) (foreground sound and speech, toast, sound-only alike), counted at the point of emission so a muted chat cannot use up the allowance.
