# Send compatibility contract

> Exact wppconnect/wa-js pins, `auditSendResult()`, and why HTTP 201 without a message id is a failure.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

- **Send compatibility contract**: executable `@wppconnect-team/wppconnect` and `@wppconnect/wa-js` versions are exact pins in `api_patches/package.json`, copied by both installers; `wpp_minimum_version.txt` is the homologated WPPConnect Server release used by setup/reinstall/update. Keep `@wppconnect/wa-version` updateable because its WhatsApp HTML catalogue expires. Every primary send endpoint runs its result through `auditSendResult()` (`messageController.ts`) before returning 201, and Python parses the same body through `core/send_contract.py`; HTTP success without a real message id is a failure. **`auditSendResult()` deliberately does not throw** — the audit happens after the message is already on the network, so throwing would land in `returnError` → HTTP 500, which `MainWindow._classify_send_exception()` calls retryable, and `MessageQueue` would resend a message that was delivered. The verdict rides back inside the 201 body under `error`, where `accepted_message_id()` turns it into a permanent failure. It reads the ACK *before* that error string, because a refusal carries both and only the ACK distinguishes "WhatsApp refused this file" (`media_unsupported_error`) from "nothing proved the send happened" (`send_not_confirmed_error`, which sends the user off to check the conversation). `/send-capabilities` is the read-only startup probe for public send functions and the private status-reaction signature.
