# Send compatibility contract

> Exact wppconnect/wa-js pins, `auditSendResult()`, and why HTTP 201 without a message id is a failure.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

- **Send compatibility contract**: executable `@wppconnect-team/wppconnect` and `@wppconnect/wa-js` versions are exact pins in `api_patches/package.json`, copied by both installers; `wpp_minimum_version.txt` is the homologated WPPConnect Server release used by setup/reinstall/update. Keep `@wppconnect/wa-version` updateable because its WhatsApp HTML catalogue expires. Every primary send endpoint runs its result through `auditSendResult()` (`messageController.ts`) before returning 201, and Python parses the same body through `core/send_contract.py`; HTTP success without a real message id is a failure. **`auditSendResult()` deliberately does not throw** — the audit happens after the message is already on the network, so throwing would land in `returnError` → HTTP 500, which `MainWindow._classify_send_exception()` calls retryable, and `MessageQueue` would resend a message that was delivered. The verdict rides back inside the 201 body under `error`, where `accepted_message_id()` turns it into a permanent failure. It reads the ACK *before* that error string, because a refusal carries both and only the ACK distinguishes "WhatsApp refused this file" (`media_unsupported_error`) from "nothing proved the send happened" (`send_not_confirmed_error`, which sends the user off to check the conversation). `/send-capabilities` is the read-only startup probe for public send functions and the private status-reaction signature; `main.py`'s `_check_send_capabilities()` speaks a narrower `status_reaction_capability_incompatible` warning (instead of the general `send_capabilities_incompatible` one) when `missing` is `["statusReaction"]` alone — that check is a chronic false positive for real sending, see below.

- **Why status-reaction lookup keeps breaking, confirmed 2026-09-20**: `reactMessage()`'s fallback chain in `deviceController.ts` used to end with `loader.ensureLazyModule('WAWebSendStatusReactionAction')`, borrowed from `@wppconnect/wa-js`'s own lazy-bundle mechanism (WhatsApp Web >= 2.3000 splits its module graph into bundles the Bootloader fetches on demand; a module whose bundle this session never needed is absent from the registry no matter how many times `searchId`/`moduleRequire` retry). Read wa-js 4.6.0's compiled `ensureLazyModule` (`node_modules/@wppconnect/wa-js/dist/wppconnect-wa.js`): it looks the module id up in its own `LAZY_MODULES` table first, and if absent returns `[]` candidate components — i.e. the Bootloader fetch never runs. That table only has two entries, both wa-js's own forward-message feature (`WAWebChatForwardMessage`, `WAWebForwardMessagesToChat`). `WAWebSendStatusReactionAction` is WinZapp's own reverse-engineered addition, not something wa-js knows about, so **`ensureLazyModule` was a guaranteed no-op for it** — that branch of the fallback chain could never rescue a cold module, independent of which WhatsApp Web build is served. This is exactly what the 2026-09-20 log showed: `moduleRequire`/`search`/`window.require` all missed because the bundle was never organically loaded this session, and the lazy-fetch fallback silently did nothing (`native-status-reaction-action-not-found`). It self-resolved whenever something else in the session (e.g. opening the Status tab) happened to trigger that bundle's real load, and broke again on a fresh session that never did — which is why reinstalling "fixed" it for a while and it always came back.

- **The fix, shipped 2026-09-20**: both `reactMessage()` and `getSendCapabilities()` fetch the Bootloader component themselves instead of routing through wa-js's table. Read wa-js's own `ensureLazyModule` further: the Bootloader instance comes from `loader.moduleRequire('Bootloader')` (unwrapping `.default` if the export is wrapped), its live component names are `Bootloader.__debug.componentMap.keys()`, and a component is fetched with `Bootloader.loadModules([name], callback, tag)`. WinZapp's copy scans `componentMap` for a candidate name (up to 6, 8s timeout each — the same shape as wa-js's own `pattern`/`MAX_DISCOVERED_COMPONENTS` fallback for its forward-message entries) and re-checks `moduleRequire('WAWebSendStatusReactionAction')` after each fetch. **The two copies (`reactMessage()`'s status-reaction branch and `getSendCapabilities()`'s probe) must stay in sync** — `tests/test_send_compatibility_probe.py::test_status_reaction_bootloader_fallback_is_mirrored_in_both_lookups` only checks both contain the same markers, not that the logic matches byte-for-byte.

- **First live result, 2026-09-20**: the combined `/status.*reaction|reaction.*status/i` pattern matched **zero of 520** scanned `componentMap` entries — `errors` came back with `winzapp-bootloader=no-candidate-components; scanned=520`. Whatever bundle actually carries `WAWebSendStatusReactionAction` is not named with both words together. Broadened to a tiered search: try the combined pattern first, then fall back to bare `/reaction/i` alone (safe against false positives — WhatsApp's own React component names carry a `.react` suffix, e.g. `WAWebForwardMessageFlow.react` from wa-js's `LAZY_MODULES`, and "reaction" is four letters longer so it never matches that suffix). If even the loose tier finds nothing, the failure detail now includes the **full sorted list of scanned component names** (`components=...`) instead of just a count — that list is what settles the real name next time this is tested live, rather than another guess. Not yet re-verified live as of this entry.
