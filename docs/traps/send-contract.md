# Send compatibility contract

> Exact wppconnect/wa-js pins, `auditSendResult()`, and why HTTP 201 without a message id is a failure.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

- **Send compatibility contract**: executable `@wppconnect-team/wppconnect` and `@wppconnect/wa-js` versions are exact pins in `api_patches/package.json`, copied by both installers; `wpp_minimum_version.txt` is the homologated WPPConnect Server release used by setup/reinstall/update. Keep `@wppconnect/wa-version` updateable because its WhatsApp HTML catalogue expires. Every primary send endpoint runs its result through `auditSendResult()` (`messageController.ts`) before returning 201, and Python parses the same body through `core/send_contract.py`; HTTP success without a real message id is a failure. **`auditSendResult()` deliberately does not throw** — the audit happens after the message is already on the network, so throwing would land in `returnError` → HTTP 500, which `MainWindow._classify_send_exception()` calls retryable, and `MessageQueue` would resend a message that was delivered. The verdict rides back inside the 201 body under `error`, where `accepted_message_id()` turns it into a permanent failure. It reads the ACK *before* that error string, because a refusal carries both and only the ACK distinguishes "WhatsApp refused this file" (`media_unsupported_error`) from "nothing proved the send happened" (`send_not_confirmed_error`, which sends the user off to check the conversation). `/send-capabilities` is the read-only startup probe for public send functions and the private status-reaction signature; `main.py`'s `_check_send_capabilities()` speaks a narrower `status_reaction_capability_incompatible` warning (instead of the general `send_capabilities_incompatible` one) when `missing` is `["statusReaction"]` alone — that check is a chronic false positive for real sending, see below.

- **Why status-reaction lookup keeps breaking, confirmed 2026-09-20**: `reactMessage()`'s fallback chain in `deviceController.ts` used to end with `loader.ensureLazyModule('WAWebSendStatusReactionAction')`, borrowed from `@wppconnect/wa-js`'s own lazy-bundle mechanism (WhatsApp Web >= 2.3000 splits its module graph into bundles the Bootloader fetches on demand; a module whose bundle this session never needed is absent from the registry no matter how many times `searchId`/`moduleRequire` retry). Read wa-js 4.6.0's compiled `ensureLazyModule` (`node_modules/@wppconnect/wa-js/dist/wppconnect-wa.js`): it looks the module id up in its own `LAZY_MODULES` table first, and if absent returns `[]` candidate components — i.e. the Bootloader fetch never runs. That table only has two entries, both wa-js's own forward-message feature (`WAWebChatForwardMessage`, `WAWebForwardMessagesToChat`). `WAWebSendStatusReactionAction` is WinZapp's own reverse-engineered addition, not something wa-js knows about, so **`ensureLazyModule` was a guaranteed no-op for it** — that branch of the fallback chain could never rescue a cold module, independent of which WhatsApp Web build is served. This is exactly what the 2026-09-20 log showed: `moduleRequire`/`search`/`window.require` all missed because the bundle was never organically loaded this session, and the lazy-fetch fallback silently did nothing (`native-status-reaction-action-not-found`). It self-resolved whenever something else in the session (e.g. opening the Status tab) happened to trigger that bundle's real load, and broke again on a fresh session that never did — which is why reinstalling "fixed" it for a while and it always came back.

- **The fix, shipped 2026-09-20**: both `reactMessage()` and `getSendCapabilities()` fetch the Bootloader component themselves instead of routing through wa-js's table. Read wa-js's own `ensureLazyModule` further: the Bootloader instance comes from `loader.moduleRequire('Bootloader')` (unwrapping `.default` if the export is wrapped), its live component names are `Bootloader.__debug.componentMap.keys()`, and a component is fetched with `Bootloader.loadModules([name], callback, tag)`. WinZapp's copy scans `componentMap` for a candidate name (up to 6, 8s timeout each — the same shape as wa-js's own `pattern`/`MAX_DISCOVERED_COMPONENTS` fallback for its forward-message entries) and re-checks `moduleRequire('WAWebSendStatusReactionAction')` after each fetch. **The two copies (`reactMessage()`'s status-reaction branch and `getSendCapabilities()`'s probe) must stay in sync** — `tests/test_send_compatibility_probe.py::test_status_reaction_bootloader_fallback_is_mirrored_in_both_lookups` only checks both contain the same markers, not that the logic matches byte-for-byte.

- **First live result, 2026-09-20**: the combined `/status.*reaction|reaction.*status/i` pattern matched **zero of 520** scanned `componentMap` entries — `errors` came back with `winzapp-bootloader=no-candidate-components; scanned=520`. Whatever bundle actually carries `WAWebSendStatusReactionAction` is not named with both words together. Broadened to a tiered search: try the combined pattern first, then fall back to bare `/reaction/i` alone (safe against false positives — WhatsApp's own React component names carry a `.react` suffix, e.g. `WAWebForwardMessageFlow.react` from wa-js's `LAZY_MODULES`, and "reaction" is four letters longer so it never matches that suffix).

- **Second live result, 2026-09-20**: the loose `/reaction/i` tier *also* matched nothing, so the fallback dumped the full sorted `componentMap` — but `main.py`'s `send_reaction()` truncates the whole HTTP response body to `response.text[:1500]` before logging it (a cap sized for the old, much shorter error message), and the ~520-name, alphabetically-sorted list got cut off before reaching anything starting with `WAWebSta...` or `WAWebReact...` — the exact range that mattered was the range that got dropped. Filtered the dump to a sample and raised the Python truncation to `response.text[:6000]`.

- **Third live result, 2026-09-20**: the sample filter itself was wrong — `/status|react|like|story|emoji/i` used bare `react`, which (unlike the tiers' own `reaction`) matches the `.react` suffix WhatsApp puts on nearly every React component name (`WAWebXyzModal.react`, etc.). `sample(248)` came back — still too big, and `response.text[:6000]` cut it off again before the interesting range. Fixed: the filter now uses the full word `reaction` (matching the tiers), not `react`.

- **Fourth live result, 2026-09-20 — the actual data, finally legible**: `sample(71)` came back complete and readable. **Not one of the 520 components contains the word "reaction" anywhere.** WhatsApp evidently bundles `WAWebSendStatusReactionAction` inside a broader status-viewer flow rather than naming a component after it — the same way `WAWebChatForwardMessage` (a wa-js `LAZY_MODULES` entry) is fetched via components named after UI flows (`WAWebForwardMessageFlow.react`), not after the module itself. From the sample, the two most plausible bundles are `WAWebStatusDrawerFlow.react` (the status viewer, where the reaction bar lives in the real UI) and `WAWebStatusQuotedFlow.react` (status-reply, an adjacent private action often shipped in the same bundle). Added as a **third tier**, tried only when both regex tiers find nothing: a short hardcoded list, filtered against the live `componentMap` before fetching (so a renamed/missing one is a no-op, not an error).

- **Fifth live result, 2026-09-20 — confirmed fixed.** One of the two tier-3 candidates (most likely `WAWebStatusDrawerFlow.react`, the status viewer bundle) registers `WAWebSendStatusReactionAction`, and status reactions now send. Gabriel confirmed live. If this regresses on a future WhatsApp Web build, check the accepted detail's `moduleSource` field first (`winzapp-bootloader[<component>]` names which of the two actually worked) before assuming the whole mechanism broke again — a future WhatsApp rename would most likely need the tier-3 candidate list updated, not the search strategy rebuilt.
- **Status posts failing with `messageSendResult=ERROR_UNKNOWN` (text, image, video, audio alike), measured 2026-09-23 on WhatsApp Web 2.3000.1048298845**: WA-JS 4.6.0 wraps `WAWebSendMsgJob.encryptAndSendMsg`, and for a `status@broadcast` record calls `encryptAndSendStatusMsg(msg, proto, reporter)` positionally inside a `try { … } catch { return null }`. Current WhatsApp's sender takes one object, `{ sendMsgRecord, msgProtobuf, metricsReporter }` (`length === 1`), so the call throws, WA-JS swallows it, and `ERROR_UNKNOWN` is all that reaches the API. The first fix wrapped `encryptAndSendMsg` too, which only works while ours is the **outermost** wrapper. Over CDP, `__winzappStatusSenderInstalled` was `true` but `encryptAndSendMsg` was WA-JS's `(...r)=>t(e,...r)`. With the real sender and `createMsgProtobuf` swapped for recorders for one fake call (nothing sent), the record reached the sender with **3 positional arguments**. `restoreStatusSender()` (`createSessionUtil.ts`) now adapts `WAWebEncryptAndSendStatusMsg.encryptAndSendStatusMsg` itself. WA-JS reads that export live (the same probe saw a replacement take effect), so wrapper order no longer matters, and WhatsApp's own object calls pass through. When statuses fail with `ERROR_UNKNOWN` again, look first at what the sender actually receives: `WPP.loader.moduleRequire('WAWebEncryptAndSendStatusMsg')`, its `.length`, and a recorder in its place. `.encryptAndSendStatusMsg.__winzappPositionalAdapter` tells "not installed" apart from "installed but bypassed", and `wppconnect.log`'s `status sender shim:` line now says whether it installed, skipped (with the length it saw) or gave up.

- **Every send route must carry the quote; `/send-mentioned` used to drop it (2026-10-01).** Testers reported that a reply which also @-mentioned someone showed as a reply in WinZapp's own list, with no error, but reached the recipients as an original message. Cause, read from the code: `send_text_message()` took the `/send-mentioned` branch whenever there were mentions and computed the quote id only in the `else`, so the quote was dropped silently (the legacy-@c.us retry dropped it too); and wppconnect's `client.sendMentioned(to, message, mentioned)` passes only `{detectMentioned, mentionedList}` to `WPP.chat.sendTextMessage` — it has no quote parameter. wa-js 4.6.0's `prepareRawMessage` handles `mentionedList` and `quotedMsg` independently and merges both, so the fix is a payload field: `/send-mentioned` accepts an optional `messageId` (same contract as `/send-reply`), and `messageController.ts`'s `sendMentionedWithQuote()` makes the library's own call plus `quotedMsg`, returning the `sendTextMessage` result untouched so `auditSendResult()` sees the same shape; without `messageId` the library call is unchanged. The rules that follow: (1) a new send route or payload builder that can carry a quote or mentions carries both, and a test builds the payload with both; (2) a status quote never takes `/send-mentioned` (`quote_is_status()` in `core/send_contract.py`): the status reply goes through `/send-reply` with the mentions dropped, since they mean nothing in a status-reply DM and `replyToStatusMessage()` ignores them; (3) the fallbacks behave as for a reply without mentions — a definite 4xx may strip the quote (and keeps the mentions, by re-sending through `/send-mentioned` without `messageId`), an ambiguous 5xx never resends, a status is never degraded. Note that the Node `returnError()` answers **every** controller failure with HTTP 500, so a quote wa-js refuses (`quoted_msg_can_not_reply`, message not found) reaches Python as an ambiguous 500 and is not resent — exactly like a reply without mentions; the 4xx fallback only fires for failures raised before the controller (auth, validation, rate limit). This needs the rebuilt `dist/`, so it reaches an install only with a release ZIP or an API reinstall; an older Node answers the new `messageId` by ignoring it, i.e. the old behaviour.
- **Forwarding goes through `forwardRuntime.ts`, not `forwardMessagesV2` (2026-10-02)**: `deviceController.forwardMessages` evaluates one in-page function that loads the unloaded Bootloader resources of the forward components and calls WhatsApp's `forwardMessages({chat, msgs, ...})` directly, because wa-js's own binding fails with `forward_messages_not_available` on builds with unresolved dependencies. The response keeps its shape (`201 {status:'success', response}`; any failure is a 500, now with a `detail` field). A rejected forward is never retried on the Node side; Python's own single retry in `forward_message` stays. Cause, rule and diagnosis ladder: `docs/traps/whatsapp-web-version-pin.md`.
- **Retry overlap: the forward is deduplicated in the page (2026-10-02)**: `forward_message` posts again after its 20 s timeout while the first request's `page.evaluate` is still running (a slow heal, or a slow WhatsApp). Without a guard the retry forwards the same messages a second time. `forwardRuntime.ts` therefore keeps `window.__winzappForwardInflight[chatId + '|' + ids]`: a request whose key is already in flight awaits the first one's result and never sends; the key is released in a `finally` (also on rejection), so a deliberate later forward is not blocked. The heal budget is 10 s so it ends well inside Python's timeout. `response` is passed through `JSON.parse(JSON.stringify())` because a result that cannot be serialized would fail the evaluate AFTER the send, a 500, and the very retry this rule exists to avoid. The same rule applies to any new send route that Python retries.
- **`keepVoice`: a forwarded voice message stays a voice message (2026-10-04)**: WhatsApp Web converts a forwarded `ptt` into a plain `audio` on the client, in `WAWebMediaForwardMediaMsg.forwardMediaMsg`: `q = msg.mediaData.toJSON()`, then `q.type = AUDIO` unless the message came from a channel — so a forwarded `ptt` is something WhatsApp itself sends and its apps display. With `keepVoice: true` in the POST (Settings > User Interface, `forward_voice_as_voice`, off by default; Python sends it only for a voice message), `forwardRuntime.ts` wraps `toJSON` of that one message for the length of that one forward so the write to `audio` is refused; everything else is still WhatsApp's own forward, and the copy keeps `isForwarded`/`forwardingScore`. Measured over CDP: the copy arrived as `type ptt`, `isForwarded true`, `forwardingScore 1`, duration and waveform intact. Three rules: the guard is **shared per message** (a `WeakMap`, removed by the last overlapping forward — two independent wrappers restore each other's function and leave one behind for good); it is taken off in a `finally`, also on a rejected forward; and it **cannot fail a send** — if WhatsApp stops converting through `toJSON`, the guard never fires, the message goes out as audio as before, and the handler logs `voice kept for N of M` (the outcome carries `voice: {asked, kept}`). `keepVoice` is part of the in-flight key, so a retry still dedupes but a keep and a plain forward of the same message are two sends.
