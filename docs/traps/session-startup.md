# Starting the API and recovering a session whose Chrome is dead

> Background launch must still wait for Node; a dead Chrome holding `userDataDir` loops CLOSED forever; two `create()`s can be in flight.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## Starting with Windows must still wait for the API (`ensure_wpp_running()`)

A foreground launch runs `ensure_api_modules_installed()` / `ensure_wpp_version()` / `ensure_wpp_running()` synchronously in `MainWindow.__init__`, so by the time `init_UI()` builds the tray icon and `post_ui_init()` starts connecting, Node is listening. A `--background` launch (autostart with Windows) handed the same three calls to a daemon thread and carried straight on — and what that bought was not a faster start but a broken one. Measured on a real boot: tray icon up and `post_ui_init` at STEP 5 by T+1.1 s, `check_wa_connection_http` refused (`WinError 10061`) at T+1.2 s, three of the six `connect_websocket` attempts spent on a dead port, Node finally answering at T+15 s, and the session then cold-started by the health checker through CLOSED → INITIALIZING → disconnectedMobile → QRCODE. Minutes of "desconectado do WhatsApp" every boot, for nothing.

**What background mode should skip is the dialog, not the wait**, and `ensure_wpp_running()` already knows the difference — its background branch polls the port for up to 300 s and never constructs `ApiStartupDialog`. So all three calls are now unconditional, and nothing appears on screen while they run (`ensure_wpp_version()` returns immediately in background mode; every dialog in the install path is behind its own `background_mode` guard, exiting rather than showing). The tray icon appearing only once the API is up is the intended consequence, not a side effect.

The reuse check ("WPPConnect already listening on this port — reusing it") also moved above the background branch, which used to spawn unconditionally: a leftover Node from a crashed run meant a second one launched only to die on `EADDRINUSE` while the poll reported success against the first — the same false success the foreground path documents, with no dialog to show it.

## A paired foreground launch builds the window before Node answers (issue #407)

The foreground start used to run inside the modal `ApiStartupDialog` and build the main window only once the port answered. Measured on a Mac launch (2026-10-05): 2.5 s of dialog — 1.4 s of WhatsApp Web catalogue check before the spawn, 1.1 s for Node to listen — in front of a window that needs nothing from Node (chat list from the database, "connecting" in the title, sends held by the MessageQueue while `_wa_connected` is False). `may_start_api_behind_window()` (`main_window/api_start_behind_window.py`) now lets an already-paired account with a complete token build the window at once; `_start_api_behind_window()` settles the port synchronously, then waits for the catalogue on a worker, spawns on the UI thread and polls on the worker.

**This is the foreground path only.** Background launches still wait in `__init__` (the section above), and first runs, `pending` accounts, paired-without-token and legacy tokens keep the dialog: each needs an answer from Node before `__init__` can go on. What that path relies on, and must keep:

- **Every thread that reaches Node before the connection is up calls `wait_for_api_start()` first** — post_ui_init, `wait_messages_set()`'s probe, the health checker, `_cleanup_abandoned_sessions_worker()`. A new one needs the same call. The cleanup is the one that bites silently: with Node refusing, its circuit breaker skips every WhatsApp logout and deletes the profiles anyway, leaving linked devices on the phone that nothing can remove.
- **`__init__`'s pairing check is not skipped, it is moved**: `_confirm_pairing_behind_window()` runs it from post_ui_init once Node answers, with the same switch-account offer, pairing dialog and registry promotion.
- **`wpp_update_may_run_now()` answers False until the start settles**, so the update prompts keep waiting for Node as they did while `__init__` sat in the dialog.
- **A Node that never answers within 300 s — or any exception in the start — ends as before**: `_show_api_startup_failure()` (the dialog path's own message and log tail), then `real_exit()`; never while `_wpp_updating`, which owns the failure, as in `ensure_wpp_running()`. The worker is wrapped so the settled event is set on every path: the waiters block without a timeout.
- **The spawn stays on the UI thread** (`wx.CallAfter`, with the `_shutting_down` check in the same turn): `_start_wpp_background()` rewrites `os.environ`, unsafe off the main thread on macOS while Cocoa builds the window. Only the catalogue wait and the port poll run on the worker, and the worker stops waiting for a spawn the main loop will never run once a quit begins.
- **`__init__` and this path share `_pair_account_at_startup()`** (`window_chrome.py`); only how the process ends differs.

## A dead Chrome can hold a session offline forever (`createSessionUtil.ts`)

When a session dies *after* its browser launched, the browser stays alive holding `userDataDir/<session>` while `client.status` goes to CLOSED. What follows is fully mechanical and unrecoverable: the health checker sees CLOSED → POSTs `/start-session` → puppeteer refuses with `The browser is already running for <dir>` → status stays CLOSED → same thing 30 s later, forever. Nothing in that loop ever touches the process holding the lock. `launchWithStaleBrowserRecovery()` kills by userDataDir and relaunches **once**. Three things make it safe and must stay: `createSessionUtil()` has already refused to run for any session not CLOSED, so a browser holding this profile is by definition one no live session owns; the kill is scoped to *this session's* userDataDir, never to "Chrome"; and the retry is bounded at one, because a profile held by something unkillable (another Windows user, a debugger, an antivirus) would otherwise spin Chrome launches forever. `forceKillByUserDataDir()` returns a promise purely so this can await it — awaiting an `undefined` would relaunch straight back into the lock — and the settle delay exists because `Stop-Process` returns before Windows releases the file handles.

**The userDataDir scan kills whoever holds the profile, which is not always who you meant.** `killBrowserOrFallback()` tries a precise process-tree kill through `wppClient?.page` first, but `wppClient` is only assigned once `create()` returns — during `create()` itself it is in the temporal dead zone, so the fallback always runs. Measured live: a `create()` started 45 s earlier against a broken profile reached its 30 s auth-probe bound and force-killed by directory — and by then WinZapp had restored the profile and a *second* session was connected and syncing on it. `03:55:50 Connected/inChat` → `03:56:01 Auth probe has failed for 30s straight` → `03:56:02 shouldClose detected in statusFind. Force-killing browser.` → `browserClose`. WhatsApp logged that session out on the next load. The scan is now refused once `clientsArray[session]` holds a *different* client, and every `shouldClose` branch clears the slot through `clearSessionSlotIfStillOurs()` — clearing it unconditionally would drop a successor's client and leave the session unreachable with its browser still running. The precise kill stays unconditional: it can only ever reach this `create()`'s own page.

**Two independent session starts can be in flight for one session.** `createSessionUtil()` refuses to run unless the status is CLOSED, and a `create()` blocked inside `waitForLogin()` has not set one yet — so the health checker's next `/start-session` is let through. Anything with a timeout inside a `create()` therefore has to assume it may fire long after it stopped being the current attempt.

## A session started with no network never comes back (`_restart_wpp_session()`)

A browser started while the machine cannot reach WhatsApp does not recover when the network does. Measured 2026-09-26 after a 2 h 17 min suspend: the wake found the page dead (`detached Frame`), `_restart_wpp_session()` closed it and POSTed `/start-session` while DNS still failed. WhatsApp Web loaded from cache, authenticated from the profile, logged `Current state: SYNCING` -> `Checking phone is connected...` and never another line. wppconnect's `waitForInChat()` polls `WPP.conn.isMainReady()` and its only exit is `deviceSyncTimeout`, which is pinned to 0 (see `api_patches/src/config.ts`), so the status sat at INITIALIZING. The network came back at 17:42 and nothing moved: the health loop skips every "active" status to avoid a second browser, and the post-resume stuck-INITIALIZING restart is gated off (`_RESUME_RESTART_STUCK_INITIALIZING`, force-kill risk).

**So the restart probes `_probe_whatsapp_host()` before the start and, with no route, leaves the session CLOSED** and stamps `_offline_start_deferred_since`. CLOSED is the one state the health loop already knows how to bring back; its auto-start now asks `_offline_start_deferral_holds()` (only when none of the other four guards blocks — it costs a HEAD) and starts the session on the first poll that reaches WhatsApp. Two things keep this from breaking what worked:

- **The probe is only trusted for long once it has answered this run** (`_whatsapp_probe_proven`, set on any success; `_prove_whatsapp_probe_once()` fires one from a CONNECTED poll so it is usually proven before a wake needs it). An unproven probe — a PAC-only proxy that Python's `requests` does not follow would fail it forever while Chrome gets through — holds the start for at most `OFFLINE_START_UNPROVEN_PROBE_CAP_SECONDS` and then starts anyway, which is exactly the old behaviour. A proven one is still capped, at `OFFLINE_START_PROVEN_PROBE_CAP_SECONDS` (3 h): the proof is usually earned on another network, and a hotel portal or an authenticated proxy only the browser gets through must not keep the account offline for good. The probe's HEAD verifies through the Windows trust store (`client/core/tls_trust.py`) first: an antivirus that intercepts HTTPS re-signs web.whatsapp.com with a root only Windows holds, certifi's bundled list refuses it with `SSLError` — a `ConnectionError` subclass, so the probe's own "no route" — and a working machine sat offline for the unproven cap. The inverse machine exists too (Windows' root updates switched off by policy, an isolated image: the system store cannot build the chain, certifi can), so an `SSLError` from the system store is retried **once** on http_pool's certifi session, and either one verifying means reachable — closer to Chrome, which trusts its own roots and the machine's. Getting this wrong in either direction is not confined to this deferral: `_probe_whatsapp_host()` also decides the automatic offline mode (`check_whatsapp_reachable()`), the startup grace (`_startup_offline_confirmed()`), the restart deferral (`_restart_wpp_session()`, `_offline_start_deferral_holds()`) and the zombie check after resume (`_restart_session_if_zombie_after_resume()`). Which errors mean offline did not change; only where the certificate is checked did.
- **A CLOSED held on purpose is not fed to `ProfileHealthTracker`** (`cs.counts_toward_profile_health()`). The tracker counts every armed CLOSED reading as a failed start cycle and restores a snapshot after three; ninety seconds of waiting for Wi-Fi must never be able to do that.
