## Audio output devices — a BASS reinit invalidates every stream (`core/sound_system.py`)

There is one process-wide BASS device, and switching it is `BASS_Free()` + `BASS_Init()`. **Every stream created before that point is dead afterwards**, which is why `MainWindow.__init__` applies the configured output device at line ~1694, *before* `load_sounds()` at ~1702 — the comment there says so. What it does not say, and what shipped a regression: `_apply_configured_audio_devices()` calls `apply_output_device()` a **second** time at ~1741, *after* the sounds are loaded. For a user on "system default" that call used to be a no-op because `_switch_to_default_device()` began with `if self.output._device == -1: return`; removing that sentinel turned the second call into a full teardown and every effect afterwards raised `5, invalid handle`, starting with the startup sound.

So the sentinel is gone but the restraint is not: `_output_device_is_healthy()` skips the reinit when BASS is already on the device asked for **and** that device still exists. The second half is what the sentinel could not check and the reason it had to go — the device BASS is bound to is a concrete index resolved when `-1` was last passed, so unplugging a wireless dongle and letting a USB device take over as default leaves BASS bound to something that no longer exists, and nothing plays until the user switches the device away and back. `handle_playback_failure()` passes `force=True`: it is reached *because* a stream failed, and BASS answering "all good" is exactly the case that needs forcing. It also must not gate on there being a configured device name — a default that moved is the commonest case, and refusing to recover there was the bug.

Three more rules learned the hard way. `BASS_Init` accepts `-1`; `BASS_SetDevice` rejects it, so the default is resolved to a real index and selected explicitly. Error **14 ("already initialized") is success**, not failure — `apply_effects_device()` usually initialised the default already, and letting that exception escape left the old device freed with nothing initialised, which is the state that produces endless `invalid handle`. And anything that plays a sound from an error path must be wrapped: `Sound.play()`'s first statement is a `BASS_ChannelStop` on a possibly-freed handle, and the global exception handler plays a sound — that raise landed inside `sys.excepthook`, so one stale handle produced two tracebacks per event and buried the real one.
