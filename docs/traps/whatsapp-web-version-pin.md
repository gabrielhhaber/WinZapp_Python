# The WhatsApp Web version pin (`client/api_patches/start.js`)

> Interception is the pin; never run unpinned; the catalogue expires; newest is not usable.

> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## The WhatsApp Web version pin (`client/api_patches/start.js`)

WPPConnect pins by default and serves the pinned build's HTML from `@wppconnect/wa-version`; WinZapp's patch changes *which* build (newest servable, never hardcoded) and *how* the substitution is installed. **Interception and the pin are the same mechanism** — serving pinned HTML means intercepting the document request. You cannot remove one and keep the other.

Three constraints, each paid for with a real bug:

- **The interception must stay document-only.** Measured: `setRequestInterception(true)` is a blanket `Fetch.enable` and puppeteer never answers a dedicated Worker's CORS requests — they hang, silently, forever. That starved `WAWebBackendWorker`, so `isBackendWorkerBridgeReady()` stayed false, so every history chunk parked at `notification_stored`. That was the "only the last ~15 messages ever load" report. Do not widen it, and do not widen the exact `urlPattern` either — matching the `?post_logout=` navigation too makes the page loop every ~10s and pairing never completes.
- **Never run unpinned.** Unpinned, WPPConnect falls back to "using latest as fallback", WhatsApp serves its newest build, and the bundled wa-js may lag it — which showed up as sending to an individual contact failing **in silence** (usync hanging, `isSendFailure` with ack 0, REST still answering 200; groups unaffected, they use sender keys). Silent send failure is worse than a loud one, especially here.
- **The catalogue expires.** Each `versions.json` entry carries `released`/`expire` (~2-month window), and `getPageContent()` only proves the HTML can be assembled *locally* — it keeps succeeding long after Meta stops serving those assets. `selectServableVersion()` now skips expired entries (expiry checked *before* the HTML read; reading ~400 files would be minutes of startup I/O). When the whole catalogue has expired, `fetchLiveWhatsappDocument()` asks Meta for the document it is serving right now and pins that — still substituted, still document-only, and by definition a build Meta serves. **Only in that branch**, never as the default, because a live build can be ahead of the bundled wa-js.

- **Newest is not the same as usable, and the failure is silent in a new way.** Serving a build is half the contract; wa-js then has to be able to *drive* it. When it cannot, the page loads and **authenticates** — the phone lists the linked device as active — but `WPP.isReady` never becomes true, `injectApi()` dies on `Waiting failed: 30000ms exceeded`, the session never leaves INITIALIZING, and the user is told only "offline", with no logout to explain it. **Do not read the 2026-09-07 outage as an instance of this** — it looked like one and was not, and the correction is the useful part. An `npm install` that morning pinned a build Meta had released 2.5 h earlier, `injectApi()` timed out exactly as above, and the obvious reading was "the pin outran wa-js". The same `wppconnect.log` refutes it: one Node process, one `Pinning WhatsApp Web to 2.3000.1046941822-alpha` line, the session on the old profile timing out and a **freshly paired session on that same pinned build reaching `Connected`/`inChat` twelve minutes later**. The build was drivable; the Chrome profile was wedged. So when this symptom appears, compare sessions within one log before blaming the pin — a second session on the same pin is the cheapest discriminator there is, and wppconnect-server 2.10.18's own docs point the same way (a long/nested `CUSTOM_USER_DATA_DIR` failing where a short one worked). What the outage *did* prove is the deadlock below: the wedged browser held `userDataDir` and nothing could restart. `selectServableVersion()` now honours the range wa-js declares in its own bundle (`supportedWhatsappWeb`, read as text by `readWaJsSupportedRange()` — never `require()`, it is a browser bundle) as the **outermost** constraint, above expiry and channel. Today that range is a floor only, so it changes no choice; the day wa-js publishes an upper bound it is respected for free. Two rules hold it together: an unparseable or unreadable range admits *everything* (excluding everything would empty the catalogue and drop us into the unpinned branch above, which is strictly worse), and a range nothing satisfies degrades to the old choice flagged `unsupported` rather than returning null. `WINZAPP_WA_WEB_VERSION` overrides the whole selection with a catalogue-verified build — the escape hatch for a build that is new, unexpired, in range and still not drivable, which is the case no automatic rule covers.

**The pin covers the main document only, and that is a skew risk, not just a staleness one (measured 2026-10-01 over CDP).** Workers and glue come from WhatsApp live. With the catalogue's newest build (2.3000.1048298845, 23 Sep) pinned, Meta's changed worker bundle asked the pinned main glue for an `EM_ASM` address it did not have: the pthread VoIP workers died with `Aborted(No EM_ASM constant found at address 1367423)` and every call failed with `WhatsApp VoIP initializer completed without becoming ready`. Chat, send and receive were unaffected, which is why it looked like a calls-only bug. `@wppconnect/wa-version@1.5.4964` (newest 2.3000.1048960956) fixed it. Details and the way calls report it: `docs/traps/voice-calls.md`.

What keeps the catalogue fresh in the field: `core/wa_version_refresh.py` stages a newer `@wppconnect/wa-version` at launch (at most every 6 hours for the same valid installation, `/latest` only, hash-verified, same major and inside the range wppconnect declares) and swaps it in just before this process spawns Node (off the UI thread), so the new pin takes effect from the Node start after the download. `start.js` reads `html/<build>.html` from the package every time a session's page is created, so the swap is skipped while any other account's Node lease is live and a package without that build's html is never swapped in; it is guaranteed only against the leases and the lock, not against a Node started by hand in between. A plain reinstall/npm install is not evidence of freshness: its lock or cached registry metadata may select an older catalogue. `wa_version_setup` preserves a newer compatible catalogue before rebuilding, checks again after npm, and refuses setup success without a usable catalogue. Offline or incompatible-latest outcomes are logged as unconfirmed freshness, not 'latest installed'. Reinstall/swap changes the identity used by the throttle; the old timestamp alone cannot suppress the new check. See the 2026-10-22 section in `voice-calls.md` for the reported wasm_contract_mismatch and the corrected lock-file evidence. Rebuilding locally does nothing for a user running a CI-built release. A user who never starts WinZapp online cannot have catalogue freshness confirmed.

### Lazy-module skew: a family of failures, first seen on forwarding (2026-10-02)

Because the catalogue now refreshes at startup, the newest builds get pinned, and WhatsApp moves modules between lazily fetched scripts from one build to the next. wa-js's `ensureLazyModule` is the weak point (it only knows `LAZY_MODULES`, and it stops as soon as a module is *registered*), so every feature that depends on a lazy module can break on a build change with nothing wrong in WinZapp. Status reactions were an earlier member of the family (`docs/traps/send-contract.md`); forwarding is the next.

**Signature**: `POST /forward-messages` answers 500 with `WhatsApp's forwardMessages function is not available in this session` (wa-js code `forward_messages_not_available`), on WhatsApp Web 2.3000.1049007170 (`@wppconnect/wa-version` 1.5.4966). Other sends are fine. Measured over CDP, not guessed:

- `WPP.chat.forwardMessages` awaits `ensureLazyModule('WAWebChatForwardMessage')` and then needs `WPP.whatsapp.functions.forwardMessages`. `window.require('WAWebChatForwardMessage')` throws `Requiring module ... with unresolved dependencies`: in the chain `WAWebChatForwardMessage -> WAWebForwardAssociatedChildren / WAWebForwardAssociationConfig -> WAWebDualUploadsSendPolicy` the last module is "not defined".
- That module is defined in a script that the page's own resource list contains and nobody loaded (`https://static.whatsapp.net/rsrc.php/v4i-Tn4/y4/l/en_US-j/aPkiNHqso7k.js`, hash `qS3/LEj`, a `Bootloader.__debug.resources` entry with `loaded=false`, belonging to the component `WAWebForwardMessageFlow.react`). wa-js returns early because its `A(name)` is true for a registered module even with unresolved dependencies. `Bootloader.loadModules(['WAWebForwardMessageFlow.react'])` resolves without fetching it, `Bootloader.getURLToHashMap()` is empty and `componentMap` (549 entries) has no entry named after the forward-chain modules.
- Appending a `<script>` for that URL to `document.head` made `require('WAWebChatForwardMessage')` export `forwardMessages` and `getForwardedMessageFields`. `WPP.chat.forwardMessages` still threw afterwards: wa-js binds `functions.forwardMessages` by module *name* when it loads, so it never binds late. Calling `require('WAWebChatForwardMessage').forwardMessages({chat, msgs, multicast, includeCaption, appendedText})` directly worked.

**The rule**: when a registered module cannot be required, load the unloaded Bootloader resources of the components that carry it, and call the module directly instead of through a wa-js function that was bound (or not) at load. `client/api_patches/src/util/forwardRuntime.ts` does this for forwarding (the heal is generic: module name + component list; only forwarding is wired). It loads only `https://static.whatsapp.net/...*.js`, shares one in-flight heal per page, remembers a successful one (`window.__winzappLazyHeal`) and never retries a forward that was rejected. When the heal cannot make the module resolvable it answers with the `require()` error text (`messageParams[1]`), which names the unresolved dependency in `wppconnect.log` and in the 500 body's `detail`. It needs the rebuilt `dist/`; an older Node keeps the old failure.

**Diagnosis ladder**: (1) `try { require(name) } catch (e) { e.messageParams }` for the unresolved dependency; (2) `require('Bootloader').__debug` `componentMap` / `resources` / `loaded` for the component that owns it and the resources not loaded; (3) scan the pinned HTML's script list (`html/<build>.html` in the `wa-version` package) for the script that defines the missing module. To check a fix without sending, evaluate the body of `forwardRuntime.ts` with an empty `messageIds`.
