# Pairing flow: nested modals, rate limits, unattended QR floods

> How `EndModal()` must be sequenced, why pairing codes are rate-limited per number, the 2.3.2 lifecycle, and the ban that an unattended code stream earns.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## Pairing flow — nested modal dialogs
`Connect.show_connection_dial()` and `show_pairing_dial()` (`client/ui/dialogs/connect.py`) are both shown via `ShowModal()`, with `pairing_dial` nested inside `connection_dial`'s own modal loop (opened from a button handler running inside it). `WebSocketClient.on_pairing_complete()` (`core/websocket_client.py`) closes them once pairing succeeds — but wx only allows `EndModal()` on the loop that is actually running, and `EndModal()` doesn't unwind its loop immediately (it only signals it; that loop keeps dispatching pending events, including any `wx.CallAfter` queued from inside it). So `connection_dial` can only be closed from `show_pairing_dial()` itself, right after its own `ShowModal()` call has genuinely returned — not from `on_pairing_complete()`, inline or via a chained `CallAfter`, which both hit a `wx._core.wxAssertionError` ("IsRunning() failed") on the still-suspended parent loop. Getting this wrong reproduces as: pairing appears to succeed (connected sound plays), but the main window and tray icon never appear, sync never starts, and nothing is logged unless you instrument `EndModal()` calls directly — `MainWindow.__init__` just never returns from `show_connection_dial()`.

**Pairing codes are rate-limited server-side, per phone number, and the quota outlives the process.** 10 codes in 12 minutes was enough to earn `IQErrorRateOverlimit` (429), which is why the first code a user asks for used to fail and the second, a minute later, worked. On wppconnect ≤ 2.3.1 the stream came from WinZapp's own side: `checkQrCode` was registered on `conn.auth_code_change` and forwarded into `loginByCode`, so a session left running after a logout kept minting codes unattended, and `wppconnect_host_layer_patch.py`'s v8 paced that with an exponential reuse cooldown capped at 4 minutes.

**2.3.2 moved that lifecycle into wa-js, so the cooldown is gone rather than ported** — `patch_host_layer_source()` now carries two patch sets and picks by matching the file, because `_apply_node_modules_patches()` runs on every launch and a WinZapp update alone never moves `node_modules`. On 2.3.2 `checkQrCode` is not registered at all when a phone number is set: `afterPageScriptInjected` subscribes `conn.link_code_change`/`_expired`/`_error` and calls `loginByCode` **once**, and `WPP.conn.startLinkDeviceCodeForPhoneNumber` reuses the active code for repeat calls, re-mints on a 195s timer and stops after 5 refreshes. What WinZapp still patches, and why each is load-bearing: `loginByCode` waits for the auth state before minting (2.3.1's upstream reached it only after `getQrCode()` produced a urlCode — calling it earlier is the measured `Invariant Violation #56367`), extracts the real browser-side error instead of the minified `t: t`, reports through `catchLinkCodeError` and retries a *transient* failure once, 20s later (upstream's single call only logs, so one hiccup ended pairing for the session); a rate-limited answer gives up immediately, since there is no loop left to slow down and retrying a 429 is what keeps it alive. **The retry ladder is bounded by the client's patience, not by the browser** — `connect.py` waits 90s for a phoneCode and then abandons the session, and the auth-state gate can spend 60s of that on its own, so the original 20s/40s/80s ladder put attempts 3 and 4 at ~120s and ~200s: minting real codes against the user's number for a dialog that had already closed with `no_pairing_code_received`. `onLinkCode` dedups, because the code now arrives both as an event and as `loginByCode`'s return value — and `loginByCode` clears `lastLinkCode` on entry, since `page.on('load')` re-enters it on every reload while wa-js's page state resets, and a stale value there would drop a perfectly good code. The `onLinkCodeExpired`/`onLinkCodeError` hooks are routed to `catchLinkCodeError` too — after the first code they are the only channel a refresh failure has. Reaching that channel is not reaching the user, though: `_phone_code_error` is only read by the 90s wait, which has returned long before either event can fire, so `WebSocketClient._announce_pairing_code_expired()` speaks both terminal names (error sound + `pairing_code_expired`) while the pairing dialog is up. **Except when WhatsApp refused on quota grounds**, where that line's own advice — cancel and try again — is what spends the quota: the hook classifies the refusal (the page-side listener walks the error's own properties instead of reading `.message`, because wa-js emits `e instanceof Error ? e : new Error(String(e))`: a real `Error` — which the quota refusal is — crosses with `name: 'IQErrorRateOverlimit'` and `value: {text: 'rate-overlimit', code: 429}` intact while its `.message` holds only whatever the minified class left there, so upstream's `.message` read throws the verdict away. The `new Error(String(e))` branch is the case the walk cannot rescue — a non-`Error` object stringifies to `[object Object]`, the walk yields `{message: "[object Object]"}`, classification degrades to `rateLimited: false` and the user hears the generic expiry line: worth knowing, and the safe direction to fail in), `phone_code_error_is_rate_limit()` reads the same shape it reads from a first-mint failure, and the announcement becomes `pairing_code_rate_limited` instead. The verdict is captured at the `wx.CallAfter` call site, not inside the announcement: `_phone_code_rate_limited` is one slot every event overwrites. Same conclusion `connect.py`'s `_on_pairing_code_error()` already reached for the first mint. **A failed refresh is terminal too, and reaches the user sooner than an expiry does** — read off wa-js's own lifecycle: `refreshLinkDeviceCode()` clears the 195s timer *before* minting and only the success continuation of the mint re-arms it, so a refresh that fails leaves `code = null`, no timer, and a rejection swallowed by its own caller's `.catch(() => {})`; `conn.link_code_expired` cannot fire afterwards either, since both of its emitters need the timer still armed or a `force_manual_refresh`. Left as a log line that stranded the user at t+195s holding a code wa-js had already discarded — the *unannounced* case arriving earlier than the announced one, and ending in the same retry-mints-a-fresh-session loop. The hook names the two apart, `LinkCodeRefreshFailed` when a code had reached the screen and `LinkCodeError` when none had (`hadCode = this.lastLinkCode != null`, read before the hook clears it), because a *first* mint failing comes through the same wa-js event and is already owned by `loginByCode`'s ladder and the 90s wait — announcing "your code expired" over a dialog with nothing on it to expire would be noise. Note the consequence of the 5-refresh bound: an attended dialog now gets roughly six codes over ~20 minutes and then silence, where v8 kept widening but never stopped. Every manual retry still mints a fresh session and resets everything, so nobody is stranded at the dialog.

**A code stream nobody is watching is a ban, not a nuisance — and `connection_mode` cannot tell you whether anyone is watching.** `WebSocketClient.on_qrcode_update()`'s two dialog-refresh branches used to key on `connect.connection_mode` alone. That attribute is written once, when the user picks a pairing method, and never reset: on an install that paired by QR it stays `"qrcode"` for the rest of the process's life. So when WhatsApp later dropped the session and WPPConnect went back to minting a fresh code every ~20-30s, every one of those events took the first branch — the sound, the spoken "O QR-CODE foi atualizado" over the conversation list, and a redraw of widgets destroyed hours earlier — and, being the first branch of an `if/elif` chain, permanently shadowed the proactive re-pairing branch below it, which was the only thing that would have told the user the session was gone. Reported live, and the account was banned for the volume of pairing attempts. Both branches now require `_is_pairing_dialog_active()`, and everything that *counts* a code as unattended goes through `_pairing_attended()`, which consults `_pairing_in_progress` as well — the dialog alone leaves the window between `on_pairing_complete()`'s `EndModal` and `messages.set`, where a just-paired install would have had its first sync closed under it (same two-signal rule, and the same reason, as `check_wa_connection_http()`'s own early return).

Surfacing it is only half of it: nothing bounded the stream itself. `autoClose`/`deviceSyncTimeout` are pinned to 0 (`client/api_patches/src/config.ts`) precisely so WPPConnect never closes a code-producing session on its own — the right answer while somebody is looking at the dialog, since a blind user needs unbounded time to pair, and the wrong one when nobody is. So a code arriving with no dialog on screen now goes to `_handle_unattended_qr()`: it opens the re-pairing dialog on the first event (paired installs), and after `_UNATTENDED_QR_LIMIT` events with still no dialog it calls `MainWindow._halt_unattended_qr_session()`, which closes the session and latches `_qr_flood_halted`. **The latch is the load-bearing half** — `check_wa_connection_http()`'s CLOSED branch fires `/start-session` on the very next poll otherwise, reviving the browser and restarting the same stream ~30s later, so the close alone buys one poll cycle rather than a fix. It is deliberately *not* folded into `_self_inflicted_teardown_expected()`: that makes `_set_wa_connected()` show "connecting" and swallow the offline announcement, and here the session is genuinely gone and the user needs to hear so — which the halt says itself (error sound + `unattended_qr_session_closed`), because by construction the flood only happens while already offline, so the next poll's `_set_wa_connected(False, …)` hits its no-change early return and says nothing. An install that never paired, which the re-pairing dialog above skips, gets that dialog opened after the halt: it is the only thing that clears the latch, so without it the app is offline for good with no route back. Nothing is wiped — token and `paired` are untouched — and the latch clears on a real reconnect and when the pairing dialog opens.
