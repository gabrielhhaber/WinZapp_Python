# The Chrome profile is the only copy of the WhatsApp login

> Snapshots, `.prev`, rejected fingerprints, the two gates on restart, WM_QUERYENDSESSION teardown, and why a restored profile is a rolled-back server.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## The Chrome profile is the only copy of the WhatsApp login (`core/profile_recovery.py`)

**WPPConnect's file token store is empty on a real install, even while a session is healthy and connected** — measured, with a CONNECTED session that had been syncing for hours. So `<global_dir>/api/userDataDir/<session>`, a Chrome profile whose IndexedDB is a LevelDB store, is the *sole* carrier of the WhatsApp login. (`WA_token` in settings is the local REST token, a different thing.) Damage it and there is no fallback: the user re-pairs, which for a blind user is the whole pairing flow again.

**The session has two halves, and losing either one strands the other.** The Chrome profile carries the WhatsApp login; `settings["privateinfo"]` carries `paired` and `WA_token`, and `sessions.json` carries the same token Fernet-encrypted alongside a per-session `status`. A confirmed logout clears the settings half while `sessions.json` still says `active` — and in that state restoring the profile achieves nothing, because `MainWindow.__init__` sees `paired` falsy and goes straight to the pairing dialog without ever starting a session. That happened live on 2026-09-09 and the recovery was to decrypt `token_enc` out of `sessions.json`, put `WA_token` and `paired` back, and relaunch. **When a profile restore appears not to work, check `paired` before concluding the snapshot is bad.**

**What actually breaks is NOT a half-written LevelDB, and the older text here saying so was wrong.** That model predicted dirty shutdowns as the cause. One day's `shutdown_audit.log` refutes it directly: four clean shutdowns produced two working launches and two broken ones, while both hard-killed runs that day came back fine. The `login_store=` fingerprint (`profile_recovery.login_store_fingerprint()`, written at the end of a shutdown and again at the next STARTUP) settled it — the two lines came back **byte-identical** across the restart that lost the session, so nothing wrote to the profile in between. Compared against a working snapshot the broken profile is structurally perfect: 387 files against 384, none missing, differing only by ordinary LevelDB compaction, and its `LOG` shows a clean `Reusing MANIFEST` / `Recovering log` / `Compacted` with no errors. Nothing on disk is damaged.

**The signature to recognise**, then, is: a complete, consistent profile that WhatsApp Web answers `post_logout=1&logout_reason=0` to about seven seconds into the page load, on an account whose phone still lists the device as linked — while an *older copy of the same profile* authenticates. That last part is what rules out a server-side device revocation: a revoked device would reject the old copy too.

**The leading hypothesis is a key-state divergence, and it is not proven.** WhatsApp advances a companion device's key state; a browser killed part-way through leaves one side committed and the other not, so the profile presents something the server refuses, while a snapshot predating the divergence still matches. Proving it needs a LevelDB reader and a diff of the WhatsApp key records between a working snapshot and a broken profile — the markers do not appear in plaintext, so a byte grep answers nothing. Both broken profiles are preserved on the reporting install for that.

**So the rule is: ask the browser to close before killing it.** `closeBrowserGracefully()` (`createSessionUtil.ts`) calls wppconnect's own `client.close()` and then waits for the process to actually exit — the call returning is not the process being gone, and the caller is usually about to relaunch against that same profile. It never throws; a failure just means the caller force-kills, exactly as it did unconditionally before. Every site with a handle to ask with now asks: `forceKillSession()`, `launchWithStaleBrowserRecovery()`, `closeSession()`'s fast path, and both Python kills (the wake-from-hibernation path and the WPPConnect update, which now go through `wait_for_profile_release()` — "wait for the release, kill only what never lets go"). It is deliberately **not** asked twice where a close has already been tried and failed. The one trap worth naming: `closeSession()`'s fast path force-killed `QRCODE`/`notLogged` sessions while its own comment said CONNECTED/open are closed gracefully "to preserve LevelDB pairing state" — right instinct, wrong half of the condition, since QRCODE is exactly what a *paired* install reports once its profile has stopped being accepted.

Three pieces of the recovery itself, and each condition is load-bearing:

- **`capture_snapshot()` only ever runs behind the same three gates** — close-session acknowledged, the session observed CLOSED, and `wait_for_profile_release()` confirming Chrome let go; never copy a profile Chrome still holds. Two call sites meet them. `_stop_wpp_server()` on a clean close, refreshing only when the snapshot is older than Settings > Cópia de segurança's `profile_backup.close_snapshot_min_hours` (24 by default, 0 = every close — `core/profile_backup.py`). And `_refresh_profile_snapshot_live()`, when `profile_backup.live_snapshot_enabled` is on: every `live_snapshot_interval_hours` it closes the session itself through `_restart_wpp_session(on_profile_released=...)`, stages the copy (`capture_snapshot(stage_only=True)`, `<snapshot>.pending`), starts the session again on those bytes, and promotes the copy only once that session reaches and stays CONNECTED — otherwise it is discarded, so a copy WhatsApp refuses never pushes the known-good generation out of `.prev`. It asks first unless `live_snapshot_confirm` is off, and only while the main window is active. One process-wide lock (`_CAPTURE_LOCK`) keeps any two copies from running together — closing WinZapp mid-copy would otherwise start the close-path copy beside it, over the same staging directory. The rest of this bullet is about the close path. It refuses when `browser_closed_cleanly` is False, when a `budget` is set (Windows owns the clock, ~5 s, and that time belongs to the flush), and when **the run never reported CONNECTED** — closing cleanly is evidence about *how* the profile was written, never about whether what was written is worth keeping. Even all of that is not sufficient: the snapshot that actually worked on the reporting install was 22.7 h old against a 24 h refresh window, one hour from being overwritten by a profile that no longer authenticated. So the generation being replaced is demoted to `<snapshot>.prev` rather than dropped, and a restore that does not hold escalates to it on the next launch (a persisted counter, cleared the moment a session reports CONNECTED).
- **A snapshot identical to the rejected profile is not a restore point.** `capture_snapshot()`'s gate is "this run reported CONNECTED", and that is not the same claim as "the state this run leaves behind will be accepted next time" — `previous_snapshot_dir()` already says so, but nothing acted on it. Measured on a user's install (2026-09-10), reading the `login_store=` fingerprints straight off `shutdown_audit.log`: a run closed cleanly at 10:52:45 with `files=21 bytes=27793052 newest=1789048351` and refreshed its snapshot from it; the next launch's STARTUP reported the *same* fingerprint and WhatsApp answered `post_logout=1&logout_reason=0` 7.6 s in; the recovery then "restored from snapshot" and was rejected again 8 s later, on the same timing. The restore had replaced the failure with an identical copy of itself — and spent the launch's one recovery attempt doing it, because the generation ladder only climbs to `.prev` on the *next* launch. `snapshot_matches_live_profile()` now compares the two before restoring: a match climbs to `.prev` **within the same launch**, and when nothing differs the user is told the profile is beyond repair rather than watching a success that changed nothing. The comparison is only sound because both copies are read the same way and `shutil.copy2` preserves mtimes; `tests/test_restore_that_restores_the_failure.py` pins that, since a copy that stopped preserving them would make every no-op restore look like a real one again. Note the same install shows the deeper fact this cannot fix: the profile that was rejected had *connected* 85 seconds earlier under a different fingerprint (`files=18 bytes=23559986`), so the state that worked was the one that session overwrote, and no local copy of it survives.
- **WinZapp cannot influence WhatsApp's key rotation — only which bytes it hands over, and whether it repeats itself.** The ratchet and the companion-device key state live inside WhatsApp Web's own JS and its server; nothing in `client/` reaches them. So the whole local surface is: never let two browsers advance one profile concurrently (`createSessionUtil.ts`'s guards), and never offer a state that has already been refused. The second half is `note_profile_rejected()` / `profile_state_was_rejected()` — a small bounded set of login-store fingerprints, the same reading `shutdown_audit.log` already records, persisted because the in-launch comparison stops working the moment a restore replaces the live profile. Cleared on CONNECTED: a state that authenticates now must not go on being refused by a verdict from before it did, and every read fails *open*, since a lost verdict costs one wasted restore while a spurious one costs the account. What the same install also shows, and what no local mechanism can fix: the rejected profile had **connected** 85 s earlier under a different fingerprint (`files=18 bytes=23559986` against the later `files=21 bytes=27793052`), so the state that worked is the one that healthy, cleanly-closed session overwrote — a clean close is not evidence that what it wrote will be accepted, which is exactly what `previous_snapshot_dir()` says and why the `.prev` generation exists.
- **`restore_snapshot()` must run with the session closed**, or it overwrites a LevelDB while Chrome holds it open. The broken profile is moved to `<profile>.broken`, never deleted. A restore that throws puts the original back, because the one impossible outcome is an account left with no profile at all.
- **The trigger is the QR, not `ProfileHealthTracker`.** A code minted for a *paired* install means WPPConnect has already decided the stored session cannot be restored — `_handle_unattended_qr()`'s own docstring said so while sending the user off to re-pair with it. The tracker cannot win that race and two attempts to make it proved it: it counts through `check_wa_connection_http()`, which returns immediately while a pairing dialog is up, so opening the dialog freezes the count for good (measured: stuck at 2 of 3 for the life of the process). `_recover_suspect_profile()` now runs from the QR handler and returns whether it started a restore; `on_give_up` fires only for an async failure, so a caller that both passes it and falls through on False cannot act twice. A user who genuinely unlinked lands here too and gets a revoked snapshot restored — accepted deliberately, since it costs one cycle before the dialog appears anyway.

  **Recover early, confirm late (issue #203).** The startup grace and `_REPAIR_DIALOG_CONFIRM_EVENTS` guard the *dialog* only — the conclusion "pair again" — never the repair. While the repair sat behind them too, a flood inside the 45 s grace spent `_UNATTENDED_QR_LIMIT` and hit the halt with a good snapshot nobody looked at, and the halt's latch then kept even a later restore from starting. Three rules hold the reordering together, each answering a defect the first attempt (PR #210, closed) had. The early repair runs only when `_profile_restore_worth_trying()` says a restore would really start (it asks the same `pick_restore_generation()` the recovery uses, spending nothing), because with nothing restorable the recovery announces a modal dead end of its own. **Codes during the restore's flight (`_profile_restore_in_flight`) are ignored and not counted**: the restore is already the halt — it opens with `close-session` and `wait_for_profile_release()` (kills once its 20 s deadline passes), and `/start-session` stays blocked throughout — while running the real halt would latch the restored profile offline and the dialog would pair over a `userDataDir` being written. "Blocked throughout" needs `_profile_restore_in_flight` itself, not `_recovery_restart_active`: that flag has **two owners**, and the power-resume restart's `finally` clears it mid-restore — after which the health poll, and that restart's own next attempt, would start Chrome over the copy. So every reader that decides whether a session may start or be torn down reads the in-flight flag too (`_session_restart_owned()` for the CLOSED auto-start and `_yield_to_in_progress_self_restart()`, `_self_inflicted_teardown_expected()`, and both restart paths right before their own `start-session`), and no early restore starts while another restart owns the session. Codes are ignored for at most `_RESTORE_FLIGHT_IGNORE_SECONDS` (180, over twice the ~81 s a restore can take to stop a browser): a restore still producing codes past that has failed to stop it, and the ceiling wins — and a restore that stalls past the halt or a re-pairing gives up rather than copying over it. And `_repair_gave_up()` asks the gates again when a restore fails, so an unconfirmed reading never ends in the `device_logged_out` box. The halt reads `seen >= _UNATTENDED_QR_LIMIT` and its own latch, not `==`: an early `return` on the limit's own code used to withhold it for the rest of the flood (the #202 shape).

Recovery runs **once per launch**, except that a restore which reaches CONNECTED earns its budget back: it has proved the snapshot works, and nothing can loop without a CONNECTED in between. That mattered live — a restored session connected and began syncing, was force-killed 11 s later by a superseded session start, and the launch's only recovery had already been spent. When there is no snapshot the user is told out loud (`profile_corrupted_repair_needed`), because this only ever happens while already offline, where `_set_wa_connected(False, …)` has hit its no-change early return and said nothing. The whole observer is wrapped at its call site inside `check_wa_connection_http()`: an exception escaping it would be counted as a failed probe, letting a bug in a diagnostic take the app offline.

**The teardown runs at WM_QUERYENDSESSION, and moving it there was the fix.** Answering the query is what releases Windows to start ending processes, and WPPConnect's Node is one of them — a separate console process CSRSS terminates during the end phase, concurrently with our own `WM_ENDSESSION` handler and with no ordering guarantee at all. Measured on one shutdown: node answering `/list-chats` in 79 ms with the session CONNECTED at 02:20:14; `WM_QUERYENDSESSION` answered TRUE at 02:20:18; the teardown starting on `WM_ENDSESSION` in the same second; `close-session` timing out on `127.0.0.1:6300` at 02:20:20; `no node pid to kill (proc gone / port free)` at 02:20:27. Node was gone within two seconds of us saying yes, so the graceful close had nothing to talk to (`pre_close_status=''` at the top of `_stop_wpp_server`), Chrome went down with it — last write to `userDataDir` at 02:20:18, the same second — and the profile came back unable to restore the session. **The budget was never the constraint; the ordering was**, and no amount of extra time at `WM_ENDSESSION` can fix a Node that is already dead. `_run_windows_session_teardown()` therefore runs from `_on_query_end_session()` before it answers — the only phase where Windows has terminated nothing. Blocking there is not a veto (not answering yet is not answering FALSE): Windows waits, and an overrun of its ~5s hung-app timeout puts us on the blocking-apps screen under the reason string, which is why the reason is created *before* the teardown and destroyed after it. `_on_end_session()` still delegates to the same method, because a session end can arrive with no query before it (`shutdown /f`, some logoff paths) — it just normally finds the work already done. The one case given up is a shutdown another app cancels after we have closed the session: wx never delivers `EVT_END_SESSION` when `bEnding` is FALSE, so the `_END_SESSION_UNSTICK_SECONDS` timer is the only thing that notices, and it now calls `_restart_wpp_after_cancelled_shutdown()` — nothing else in the app restarts a dead Node *process*, since the health checker only re-issues `/start-session`, which needs a server to talk to.

**Both Windows shutdown handlers audit as their first statement.** That same 159-launch file carried *zero* lines from either, which makes "Windows asked and the teardown never finished" and "Windows never asked" — opposite fixes — indistinguishable. `log.log` cannot settle it: it is truncated every launch, so the run that mattered is already gone. The pre-existing audit line in `_on_end_session` sits after the lock, after the already-tearing-down branch that returns without auditing, and after the safety timer, so it answers nothing.

## Two gates, and `_restart_wpp_session()` only had the first

`_stop_wpp_server()` waits for CLOSED **and** for `wait_for_profile_release()`, and its own comment says why: "This is the first of TWO gates — the second is the one that says Chrome stopped writing. Neither substitutes for the other." `_restart_wpp_session()` — the in-place restart the suspend/resume path escalates to when the page comes back a detached frame — waited only for CLOSED. Measured 2026-09-10 after a 5.5-hour suspend: `close-session -> 200` at 18:34:09.496, `status-session -> CLOSED` at .536, `start-session -> 200` at .576, `Session Unpaired -> post_logout=1&logout_reason=0` nine seconds later. **Eighty milliseconds** between the close and a replacement browser opening the same login database, against a Chrome that had a whole resumed session's state to write back — and the wait that was skipped there took **20 s** when the recovery finally ran it at 18:36:01. That is how a *suspend* destroys a profile, which otherwise reads as impossible since nothing is killed by suspending. The wait is sized at 25 s for that reason, and a browser that never lets go still starts (refusing would strand the account; `createSessionUtil`'s stale-lock recovery is the net).

**A restored profile is a rolled-back server, and its silence is not evidence of a deletion.** `restore_snapshot()` puts WhatsApp Web's own store back to whenever the snapshot was taken — up to `SNAPSHOT_MAX_AGE_SECONDS`. Measured on the same install: a snapshot from 09-09 21:20 restored at 09-10 18:36, so the browser returned knowing **21 hours less than WinZapp's database did**. `_reconcile_active_conversation_with_remote()` reads "the server has not got this message" as "the phone deleted it", so it began mirroring that rollback — deleting correctly-synced history from the only complete copy there was. `_remote_deletions_untrusted` latches on a successful restore and suspends the mirroring for the rest of the launch: a genuine phone-side deletion missed until the next launch is cosmetic, a mirrored rollback is irreversible, and only one of those is worth risking. Note this got sharper, not milder, once `remove_messages_by_id()` was fixed to remove records with no rendered row — before that, the mirroring silently failed on exactly the ids a rolled-back store reports missing.
