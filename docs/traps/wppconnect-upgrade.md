# Upgrading the vendored WPPConnect Server

> What the audit actually has to check when `wpp_minimum_version.txt` moves — and the dependency-pin trap.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## Upgrading the vendored WPPConnect Server — what the audit actually has to check

`wpp_minimum_version.txt` is the exact tag fresh installs get and the floor of what the periodic check offers (a newer release is offered as a recommended update, see `updater-channels.md`): `setup_api.py` checks that tag out, so every fresh install and every in-app "reinstall API" gets exactly it. Bumping it is therefore a real change, and the check that matters is **not** the release notes — it is `gh api repos/wppconnect-team/wppconnect-server/compare/v<old>...v<new>` intersected with `CUSTOM_ROOT_FILES + CUSTOM_SRC_FILES`. Anything in that intersection is upstream work the restore silently discards; anything outside it flows through untouched.

**`python .github/scripts/audit_wpp_upgrade.py <old> <new>` runs that whole comparison** — the intersection above, the dependency changes split into the ones WinZapp overrides and the ones upstream's own ranges govern, and whether the homologated pair moved — plus whether upstream's exactly-pinned `engines.node` still matches the Node WinZapp ships — and exits 1 only when a human actually has to look (a failure to *perform* the audit, a typo'd tag or an unauthenticated `gh`, is exit 2, because "found something" and "could not check" are opposite situations and the first must not be dismissed as the second). It imports the three lists from `setup_api.py` rather than restating them, so it cannot answer against a stale copy of the very thing it checks, and it compares **both** sides of a rename — upstream renaming a file WinZapp patches would otherwise read as clean while the restore quietly left the patch behind at the old path. It is an aid to the reasoning below, not a replacement for it: a clean exit still leaves the judgement calls (whether a flagged pair move is worth re-homologating, whether a discarded change matters) to a person. Run it before touching the pin, then re-run `setup_api.py` and confirm all six current `node_modules` patch paths (host, status, sender, welcome, browser and wa-js) still report success. The worked examples below retain the patch set present when those upgrades were measured.

**The dependency pins need the opposite reasoning, and getting it backwards is the trap.** `_PATCHED_DEPENDENCY_KEYS` is a deliberately narrow list, so upstream's own ranges govern everything else — which is how the 2.10.20/2.10.21 `multer` and `sharp` **security** bumps arrive without us doing anything. Upstream declares `"@wppconnect-team/wppconnect": "^2.3.3"`; WinZapp's exact `"2.3.4"` overriding that caret is the point of the send-compatibility contract, not drift to be reconciled. Two things follow: upstream moving its caret is not by itself a reason to move our pin (check npm for what the caret actually resolves to), and `api_patches/package.json` holds stale entries for dependencies *not* in that list (`multer` at `^1.4.5-lts.2`, `sharp` at `^0.34.5`) which are inert and must not be "fixed" — the merge never reads them. Its `"version"` field is stale for the same reason.

Also note what an incremental re-run does *not* refresh: `npm install` over a preserved `node_modules` keeps what is already resolved, so a local rebuild can sit on older transitive versions (measured after bumping to 2.10.21: `multer` still 2.2.0 where a fresh install resolves 2.3.0, `@wppconnect/wa-version` still 1.5.4490 against 1.5.4834 on npm). Fresh installs and CI get the newer ones. Same conclusion as the wa-version catalogue note below — judge a user's tree by when they last reinstalled, not by the tag.

**2.10.18 → 2.10.21, as a worked example.** Three releases, and the only source changes were `src/config.ts` and `src/index.ts` — both files WinZapp patches. Upstream (2.10.19, commit b66881b) added `dotenv.config({ override: false })` to `config.ts` and deleted the dead `//require('dotenv').config();` from `index.ts`. **Both stay overridden, and that is now load-bearing rather than incidental**: WinZapp's `config.ts` is not a variant of upstream's but a different design — upstream resolves every setting from `process.env`, WinZapp hardcodes them and reads exactly one variable, `WINZAPP_USER_DATA_DIR`. So dotenv has nothing to feed here, and the one thing it *could* reach is the path to the Chrome profile that carries the WhatsApp login, computed per install and per account by `main.py` — the single value that must never come from a file next to the exe. `override: false` protects a variable we inject and says nothing about one we do not. The reasoning is written at the top of `api_patches/src/config.ts` (a rebase reads that file, not this one) and pinned by `tests/test_api_patch_env_divergence.py`.

The one live consequence: upstream's `src/config.test.ts`, added in the same commit, fails all three of its cases against WinZapp's `config.ts` by design. It is free only because nothing here runs jest — `setup_api.py` and `build.py` only ever run `npm run build`, which is `tsc` plus babel and executes no assertion. Note it sits at `src/config.test.ts`, *outside* `tsconfig.json`'s `src/tests*` exclude, so it is type-checked and compiled into `dist/` as dead code; that is upstream's own behaviour and harmless. The same test file guards the "nothing runs jest" half.

## An export name can identify the wrong native module (2026-10-17)

wa-js 4.7.1 discovers `findOrCreateLatestChat` by the presence of that export.
Both `WAWebFindChat` and `WAWebFindChatAction` export it. On the measured runtime
the discovery selected `WAWebFindChat`, whose default lookup reads IndexedDB;
the action supplies `WAWebChatGetExistingBridge.getExisting`, which checks the
non-stale ChatCollection cache and materializes database rows as ChatModels.
With a cached chat absent from disk, the lower-level binding throws
`findChat: new chat not found`; with a disk record it can return a raw row.
An offline reproduction using the captured native factories confirmed both
paths, before and after LID migration, without sending a message.

`patch_chat_lookup_bundle()` in `core/wppconnect_wa_js_patch.py` selects the
action by its native module name, matching wa-js's adjacent explicit bindings.
It runs alongside the independent persona-id patch in setup, build, and every
app startup. Test the selected function's behavior when duplicate export names
exist, not just whether patching changed a string. This fixes the binding; it
cannot recover cryptographic identity records lost when origin storage is reset.

## Moving the library pair — wppconnect 2.3.3 → 2.3.4 with wa-js 4.6.0 → 4.6.1 (2026-10-02), as a worked example

The server tag (2.10.30) did not move; only the two pinned libraries did. The audit script above does not cover this, because it compares *server* tags. This is what was done instead, and the order matters.

**1. Diff the package tarballs, not the release notes.** `npm pack` both versions of both packages into a scratch directory and compare. For `@wppconnect-team/wppconnect` the answer was immediate and decisive: 2.3.3 → 2.3.4 changed `CHANGELOG.md` and `package.json` (its wa-js range `^4.6.0` → `^4.6.1`) and nothing else — `dist/` was byte-identical. So none of the four `node_modules` patch targets (`host.layer.js`, `status.layer.js`, `sender.layer.js`, `welcome.js`) can have moved, and the real change is wa-js. A "wppconnect bump" can be a wa-js bump in disguise: when the library's own number moves, look at what its dependency ranges resolve to.

**2. Diff the wa-js bundle per module.** `dist/wppconnect-wa.js` is one minified webpack bundle (518,065 → 523,313 bytes). Webpack ids are stable between the two builds, so split it on the `<id>(e,t,r){` boundaries, key each module by id, and diff only the ids whose text differs (61 of 764, plus 7 new). Most of those 61 are the minifier renaming one-letter locals (`h`→`b`) and differ in nothing else; normalise by reading each diff, not by trusting the size. Name each module by its exports (`t.offer=`, `t.sendRawStatus=`) or strings (`WAWebGroupCreateJob`, `LAZY_MODULES`) and then map the real changes against what WinZapp touches (`git grep` for `WPP.`, `functions.`, `loader.`, `encryptAndSendStatusMsg`, `startWAWebVoipCall`). The module-level reading, and its verdict per WinZapp touchpoint:

- `call.offer` now calls `startWAWebVoipCall(peer, isVideo, 8, 5, null, { entryTrust: 'user_gesture' })` and polls `CallStore` for the call. It is the very call `callController.ts` has made itself since PR #286, with the same arguments. Ours stays the primary path (proven on a real account, identical on 4.6.0 and 4.6.1); the `WPP.call.offer` fallback now works on 4.6.1 where it used to hang.
- `sendRawStatus`'s wrapper now chooses the call shape from `encryptAndSendStatusMsg.length`: 1 → the object form, otherwise positional. It reads the export live, like our adapter, so the two do not double-wrap: the adapter has length 1, receives the object and passes it through; on 4.6.0 it still converts the positional call. Pinned by `tests/test_status_sender_adapter.py` against both call sites.
- The loader's "registered" test became "registered **and** requireable" (`e in moduleRequire.m && !!moduleRequire(e)`), which is exactly the unresolved-dependency state `forwardRuntime.ts` heals (`WAWebDualUploadsSendPolicy`, `docs/traps/whatsapp-web-version-pin.md`). `ensureLazyModule` therefore goes on to bootload the components instead of returning early, and `LAZY_MODULES` grew from two entries to ten (group creation, invite code, community, privacy, profile name, event link; still none of WinZapp's own). Forwarding may now work through wa-js by itself; the heal only runs when the module is not already usable, so it stays harmless either way. Not provable without a live session.
- A miss in the module search now expires after one second on the `meta` loader instead of lasting until the module count changes, and a module whose `moduleRequire` returns nothing is skipped. Correct, but every export getter whose module cannot be found now re-scans the registry once a second: worth watching for CPU if a binding is permanently missing.
- `conn` registers its `Stream` events with a bounded retry (60 s) when `Stream` is not there yet. WinZapp subscribes to none of `conn.stream_*`; unaffected.
- wa-js forces `web_media_encrypt_upload_in_worker_enabled` to false by wrapping `getABPropConfigValue`, so media is encrypted and uploaded on the page's main thread. `sendFileMessage` itself is unchanged (renames only), so `watchMediaUpload`'s `change:mediaData.mediaStage` events and the chunked Node → page transfer are untouched; what changes is where the work runs for a large file.
- `WPP.group.create`, `getInviteCode`, `revokeInviteCode` and the profile-name setter now bootload their lazy module first, and `setDescription` accepts the object-argument form. These are reached through the server's own group routes and wppconnect's `group.layer.js`, with no WinZapp wrapper in between.
- `chat.list` / ChatStore bindings and `exportModule` (only a null guard) changed in no way `/list-chats` or `listChatsDiag` depends on.
- `supportedWhatsappWeb` is still `>=2.3000.1038792969-alpha`, so start.js's range check is unchanged.

**3. A path that needs a change on the new library must also work on the old one**, because "Continue without updating" keeps the old `node_modules` under the new app's `dist/`. Nothing in this upgrade needed a Node change, so there was nothing to make dual. Had something, feature-detect (`typeof`, `.length`) as the status adapter does, and if a path cannot work on the old library say so and make the reinstall mandatory rather than optional.

**4. The drift gate only saw wppconnect.** `wppconnect_library_drift()` compared `@wppconnect-team/wppconnect` alone, so a bump of wa-js on its own (the same wppconnect, a different bundle in the page) would have forced no reinstall. `core/wpp_runtime.library_drifts()` now compares both packages, exact pins only, and the prompt names the drifted library and versions. This upgrade changes both, so the prompt is shown to everyone who updates either way; the extension protects the next wa-js-only release.

**5. Verify on a real tree.** One isolated `setup_api.py`: all four `node_modules` patches report the same lines as before (their anchors live in the byte-identical wppconnect `dist/`), `npm run build` exits 0, node_modules holds 2.3.4 and 4.6.1.

## 2.10.48 → 2.10.52 (2026-10-14)

The first bump since 2.10.27 with upstream **source** changes, and the one that shows why the audit is not optional: `src/controller/miscController.ts`, which WinZapp does not override, now imports `cleanupSession` from `src/util/sessionUtil.ts`, which it does. Restoring our 2.10.48-era `sessionUtil.ts` over 2.10.52 made `npm run build:types` fail, so a server update to 2.10.49+ cannot build with the patches of a WinZapp release that bundles 2.10.48. Only a WinZapp release carrying the ported patches fixes that for users.

`audit_wpp_upgrade.py 2.10.48 2.10.52` flagged seven overridden files. Each was merged three ways (base 2.10.48, ours, theirs 2.10.52, `git merge-file`), and decided as follows:

- `src/util/sessionUtil.ts`, `src/routes/index.ts`: merged cleanly. `cleanupSession()` (a `CLOSING` reservation of the slot while a session is torn down) and `clientsArray` as a `Record` arrive; `/logout-session` no longer goes through `statusConnection`, so the logout of an abandoned session (`session_tokens._logout_abandoned_session`) is answered instead of 404.
- `src/controller/sessionController.ts`: **`closeSession` stays ours.** Its `CLOSING` marker, the bounded close and the force-kill are what WinZapp's shutdown polls (`_wait_for_session_flushed`) and were measured in the field; upstream's `cleanupSession()` version solves a subset of the same problem. `logOutSession`, which WinZapp never changed, is upstream's new one (name validated, cleanup awaited before answering).
- `src/util/createSessionUtil.ts`: **stays ours** apart from upstream's session-name check (`^[A-Za-z0-9_-]+$`, the allowlist `connection_state._valid_session_name()` already applies). Upstream's `ownsAttempt()` copies the client object per attempt and closes late browsers; ours owns an attempt through `ownClient`, `clearSessionSlotIfStillOurs()` and `shouldClose`. Mixing the two designs is how a successor's slot gets overwritten. Also kept: `customUserDataDir + session`, not upstream's `path.resolve()`; the result is the same folder (WinZapp's variable ends in a separator) but the literal is what `forceKillByUserDataDir()` matches in Chrome's command line.
- `src/util/functions.ts`: upstream's webhook allowlist and retries, and `autoDownloadMaxSize` (skip inlining large media), with our lazy `require` of the S3 SDK kept inside `if (uploadS3)`.
- `src/config.ts`: the new `webhook` fields as upstream's defaults, **as constants** — this file reads no environment variable but `WINZAPP_USER_DATA_DIR` (see its header). WinZapp sets no webhook, so none of them takes effect.
- `src/controller/deviceController.ts`: `onlyNewsletter`, `onlyCommunities` and `onlyArchived` forwarded the way ours builds the options; our `listChatsWithDiag()` hands them to `WPP.chat.list` unchanged.

Dependencies: only `tsx` (dev) moved; the homologated pair (wppconnect 2.3.4, wa-js 4.6.1) and `engines.node` did not, so the six `node_modules` patches are untouched.

Verified on a scratch checkout of 2.10.52 with the patches laid over it as `setup_api.py` does and the installed `node_modules` linked: `tsc --noEmit` and `npm run build` pass. Jest, against the same run on 2.10.48 with the previous patches: every WinZapp test passes, and upstream's new `webhookRetry` and `autoDownload` suites pass against our `functions.ts`. Upstream's tests that fail are the known divergences — the twelve already failing on 2.10.48 (`config.test.ts`, `statusConnection`, `forwardMessages`, the optional webhook listeners) plus the new ones that assert upstream's own designs we did not take: six `createSessionUtil` "initialization ownership" cases, `listChats` calling `client.listChats` (ours evaluates `WPP.chat.list` in the page), and two `sessionLifecycle` cases (a stub logger without `info`; a close that rejects leaving the slot in `ERROR`, where ours force-kills and frees it).

Nothing WinZapp calls was removed or renamed.
- `patch_wa_js_source()` (the Meta AI `personaId` guard) reports `applied` on the 4.7.1 bundle.
- `chatListsRuntime.ts` compared `wpp.version` with the literal `'4.6.1'`: on any other version a missing legacy `labelsEditingEnabled` gate meant `runtime_incomplete`, i.e. no list editing. 4.7.1 makes that gate optional for its own calls (it is in `IGNORE_FAIL_MODULES`) and exposes the same native modules, so `'4.7.1'` joins `'4.6.1'` in `nativeContractVersions`; every other version still fails closed (tests pin 4.7.0, 4.7.2, 4.8.0).
- The drift gate (`library_drifts()`) needed no change: it reads exact pins, so an installed 4.6.1 against a pinned 4.7.1 asks for the reinstall, and "Continue without updating" keeps the old libraries with the old pin text.

**Trap.** Anyone who reinstalls or updates WPPConnect gets the newest WhatsApp Web build, whatever the app version. When a send route answers 201 with `failed:` in its text, look at what changed in WhatsApp Web (`npm view @wppconnect/wa-version time`) before looking at the client.
