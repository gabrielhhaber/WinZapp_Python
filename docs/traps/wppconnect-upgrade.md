## Upgrading the vendored WPPConnect Server — what the audit actually has to check

`wpp_minimum_version.txt` is an exact tag, not a floor: `setup_api.py` checks that tag out, so every fresh install and every in-app "reinstall API" gets exactly it. Bumping it is therefore a real change, and the check that matters is **not** the release notes — it is `gh api repos/wppconnect-team/wppconnect-server/compare/v<old>...v<new>` intersected with `CUSTOM_ROOT_FILES + CUSTOM_SRC_FILES`. Anything in that intersection is upstream work the restore silently discards; anything outside it flows through untouched.

**`python .github/scripts/audit_wpp_upgrade.py <old> <new>` runs that whole comparison** — the intersection above, the dependency changes split into the ones WinZapp overrides and the ones upstream's own ranges govern, and whether the homologated pair moved — plus whether upstream's exactly-pinned `engines.node` still matches the Node WinZapp ships — and exits 1 only when a human actually has to look (a failure to *perform* the audit, a typo'd tag or an unauthenticated `gh`, is exit 2, because "found something" and "could not check" are opposite situations and the first must not be dismissed as the second). It imports the three lists from `setup_api.py` rather than restating them, so it cannot answer against a stale copy of the very thing it checks, and it compares **both** sides of a rename — upstream renaming a file WinZapp patches would otherwise read as clean while the restore quietly left the patch behind at the old path. It is an aid to the reasoning below, not a replacement for it: a clean exit still leaves the judgement calls (whether a flagged pair move is worth re-homologating, whether a discarded change matters) to a person. Run it before touching the pin, then re-run `setup_api.py` and confirm all four `node_modules` patches still report applied.

**The dependency pins need the opposite reasoning, and getting it backwards is the trap.** `_PATCHED_DEPENDENCY_KEYS` is a deliberately narrow list, so upstream's own ranges govern everything else — which is how the 2.10.20/2.10.21 `multer` and `sharp` **security** bumps arrive without us doing anything. Upstream declares `"@wppconnect-team/wppconnect": "^2.3.3"`; WinZapp's exact `"2.3.3"` overriding that caret is the point of the send-compatibility contract, not drift to be reconciled. Two things follow: upstream moving its caret is not by itself a reason to move our pin (check npm for what the caret actually resolves to), and `api_patches/package.json` holds stale entries for dependencies *not* in that list (`multer` at `^1.4.5-lts.2`, `sharp` at `^0.34.5`) which are inert and must not be "fixed" — the merge never reads them. Its `"version"` field is stale for the same reason.

Also note what an incremental re-run does *not* refresh: `npm install` over a preserved `node_modules` keeps what is already resolved, so a local rebuild can sit on older transitive versions (measured after bumping to 2.10.21: `multer` still 2.2.0 where a fresh install resolves 2.3.0, `@wppconnect/wa-version` still 1.5.4490 against 1.5.4834 on npm). Fresh installs and CI get the newer ones. Same conclusion as the wa-version catalogue note below — judge a user's tree by when they last reinstalled, not by the tag.

**2.10.18 → 2.10.21, as a worked example.** Three releases, and the only source changes were `src/config.ts` and `src/index.ts` — both files WinZapp patches. Upstream (2.10.19, commit b66881b) added `dotenv.config({ override: false })` to `config.ts` and deleted the dead `//require('dotenv').config();` from `index.ts`. **Both stay overridden, and that is now load-bearing rather than incidental**: WinZapp's `config.ts` is not a variant of upstream's but a different design — upstream resolves every setting from `process.env`, WinZapp hardcodes them and reads exactly one variable, `WINZAPP_USER_DATA_DIR`. So dotenv has nothing to feed here, and the one thing it *could* reach is the path to the Chrome profile that carries the WhatsApp login, computed per install and per account by `main.py` — the single value that must never come from a file next to the exe. `override: false` protects a variable we inject and says nothing about one we do not. The reasoning is written at the top of `api_patches/src/config.ts` (a rebase reads that file, not this one) and pinned by `tests/test_api_patch_env_divergence.py`.

The one live consequence: upstream's `src/config.test.ts`, added in the same commit, fails all three of its cases against WinZapp's `config.ts` by design. It is free only because nothing here runs jest — `setup_api.py` and `build.py` only ever run `npm run build`, which is `tsc` plus babel and executes no assertion. Note it sits at `src/config.test.ts`, *outside* `tsconfig.json`'s `src/tests*` exclude, so it is type-checked and compiled into `dist/` as dead code; that is upstream's own behaviour and harmless. The same test file guards the "nothing runs jest" half.
